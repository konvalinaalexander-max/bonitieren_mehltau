9.1 So arbeitest du mit Claude

Du arbeitest in Claude Code: im Browser unter claude.ai/code oder im Reiter „Code“ der Claude-App. Eine Sitzung ist ein Gespräch, in dem Claude an deinem Repository arbeitet. Claude kopiert das Repository dafür auf einen Rechner in der Cloud, schreibt dort den Code, lässt die Tests laufen und lädt das Ergebnis als eigenen Zweig zu GitHub hoch. Dein Hauptstand, der Zweig main, bleibt unberührt, bis du die Änderung übernimmst.

  1. Sitzung starten. Claude Code öffnen, unter dem Eingabefeld das Repository bonitieren_mehltau auswählen, den Kopier-Prompt aus 9.7 einfügen, eckige Klammern ersetzen, absenden.
  2. Plan bestätigen. Claude nennt zuerst einen kurzen Plan und offene Fragen. Du antwortest in normalen Worten. Verstehst du etwas nicht, schreib: „Erkläre mir das ohne Fachbegriffe.“ Noch sicherer: Wählst du vor dem Absenden im Modus-Feld neben dem Eingabefeld „Plan“, ändert Claude keine Datei, bevor du den Plan freigegeben hast.
  3. Claude arbeitet. Das dauert Minuten bis etwa eine Stunde. Du kannst das Fenster schließen – die Sitzung läuft in der Cloud weiter.
  4. Pull Request. Wenn Claude fertig ist, lädt es seinen Zweig zu GitHub hoch und erklärt, was es gemacht hat. Die Kopier-Prompts bitten Claude, den Änderungsvorschlag selbst anzulegen. Klappt das nicht, tippst du auf die Änderungsanzeige (z. B. „+42 −18“) und oben in der Änderungsansicht auf „Create PR“ – als normalen Pull Request, nicht als Entwurf („Draft“), denn einen Entwurf kannst du nicht direkt übernehmen. Du bekommst einen Link zum Pull Request auf GitHub.
  5. Automatische Tests abwarten. Im Pull Request laufen die Tests von selbst. Grüner Haken: alles bestanden. Rotes Kreuz: nicht übernehmen, sondern Claude in derselben Sitzung Bescheid sagen.
  6. Auf dem Box-Handy testen. Nach Claudes Test-Anleitung und der Checkliste in 9.8.
  7. Rückmeldung oder übernehmen. Stimmt etwas nicht, schreibst du es in dieselbe Sitzung. Claude bessert auf demselben Zweig nach, der Pull Request aktualisiert sich von selbst. Auch nach Tagen kannst du die Sitzung in der Liste wieder öffnen – das Gespräch ist noch da. Passt alles: auf GitHub „Merge pull request“ und dann „Confirm merge“.
  8. Live. Meist nach 1–2 Minuten ist die neue Version online (laut GitHub kann es bis zu 10 Minuten dauern). Öffnest du die App mit Internet, meldet sie „Neue Version“.
  9. Nächster Baustein, neue Sitzung. Die alte Sitzung kannst du archivieren. Jeder Baustein bekommt eine frische Sitzung.

Claude hat kein Gedächtnis zwischen Sitzungen

Jede Sitzung beginnt bei null. Was Claude wissen muss, steht deshalb in Dateien im Repository: CLAUDE.md (Projektregeln), docs/SPEZIFIKATION.md (Zahlen und Entscheidungen) und docs/FORTSCHRITT.md (welcher Baustein fertig ist, was offen ist). Alle drei legt oder pflegt Claude selbst. CLAUDE.md liest Claude Code zu Beginn jeder Sitzung sogar von selbst; die Kopier-Prompts in 9.7 lassen sie ab B2 zur Sicherheit ausdrücklich lesen.

Tipp

Sitzungen verbrauchen das Nutzungskontingent deines Claude-Abos – gemeinsam mit deiner übrigen Claude-Nutzung. Kleine, klar umrissene Aufträge kommen schneller zum Ziel als ein Riesenauftrag – und sind leichter zu testen.

So nutzt du die Prompts

Jeder Kopier-Prompt in 9.7 ist vollständig – kopier ihn ganz, auch den Schlussabsatz „Arbeite …“. Er sorgt dafür, dass Claude zuerst einen Plan zeigt, Tests schreibt, die Dokumentation pflegt und dir erklärt, wie du testest. Stellen in eckigen Klammern ersetzt du. Reicht eine Sitzung nicht, schreib nach dem Übernehmen in einer neuen Sitzung: „Mach bei B5 weiter, lies docs/FORTSCHRITT.md.“

Wenn Claude eine Datei für GitHub Actions nicht hochladen darf

Die Anweisungen für GitHub Actions liegen im Ordner .github/workflows/. Stand 09/2026 lehnt GitHub es ab, wenn Claude solche Dateien aus einer Cloud-Sitzung hochladen will (Fehlermeldung „refusing to allow … workflow …“). Rechne also damit, dass du solche Dateien selbst anlegst (meist in B1 für die Tests und in B3 für die Veröffentlichung); Claude nennt dir Zweig, Dateinamen und Inhalt. Auf GitHub über der Dateiliste den Zweig wählen → „Add file“ → „Create new file“ → Namen mit Ordnern eintippen, z. B. .github/workflows/tests.yml (jeder Schrägstrich legt einen Ordner an) → Inhalt aus Claudes Antwort einfügen → „Commit changes …“ → „Commit changes“. Danach Claude in der Sitzung Bescheid sagen. Das ist die einzige Ausnahme von der Regel „Nicht selbst am Code ändern“ (9.9).

9.3 Hosting einrichten

Die App ist eine Webseite und braucht deshalb einen Platz im Internet (Hosting, Kapitel 3.5). Nur über eine verschlüsselte Adresse (HTTPS) darf eine Webseite die Kamera benutzen – alle drei Dienste bieten das. Claude bereitet alles vor, was sich mit Dateien erledigen lässt. Die Klicks in deinen Konten machst Du: Einstellungen bei GitHub, Konto bei Netlify oder Cloudflare, App auf dem Handy installieren. Gib Claude nie deine Passwörter.

GitHub Pages (Standardweg)

  1. Claude bereitet vor. Im Baustein B3 legt Claude eine Anweisung für GitHub Actions an (.github/workflows/), die App, Werkstatt, Analyse-Kern und Bibliotheken veröffentlicht (wahrscheinlich legst du diese Datei selbst an, Kasten in 9.2). Möchtest du die Werkstatt schon in Etappe 4 per Link öffnen, bitte Claude in B2 darum.
  2. Quelle umstellen. Im Repository oben „Settings“ → in der linken Leiste im Abschnitt „Code, planning, and automation“ (in älteren Ansichten „Code and automation“) auf „Pages“ → unter „Build and deployment“ bei „Source“ die Option „GitHub Actions“ wählen. Das machst du am besten, bevor du den Pull Request übernimmst.
  3. Übernehmen und zuschauen. Pull Request übernehmen. Im Reiter „Actions“ läuft danach die Veröffentlichung; ein grüner Haken heißt: online.
  4. Adresse notieren. Unter „Settings“ → „Pages“ steht die Adresse mit dem Link „Visit site“. Sie hat die Form https://konvalinaalexander-max.github.io/bonitieren_mehltau/; die App liegt in einem Unterordner, den Claude dir nennt (z. B. …/app/). Adresse ins Projekttagebuch.
  5. Auf dem Box-Handy installieren. Adresse in Chrome öffnen, Menü (drei Punkte) → Eintrag zum Installieren wählen. Je nach Chrome-Version heißt er z. B. „Installieren und Verknüpfung erstellen“ oder „Zum Startbildschirm hinzufügen“. Dann „Installieren“ antippen. Danach liegt ein App-Symbol auf dem Startbildschirm.

Achtung: nur die App veröffentlichen

Die Webseite ist für jeden erreichbar, der die Adresse kennt – auch wenn das Repository privat ist (Kapitel 3.5). Unkritisch, denn die Messdaten bleiben auf dem Handy und in deinen Exporten. Veröffentlicht werden aber nur App, Werkstatt, Kern und Bibliotheken, nie referenzbilder/ oder docs/. Ist dein Repository privat, brauchst du für GitHub Pages ein kostenpflichtiges GitHub-Abo; ohne Abo nimm eine der Alternativen.

Alternative: Netlify oder Cloudflare Pages

Beide verbinden sich mit deinem GitHub-Repository und veröffentlichen die App nach jedem Merge von selbst. Ihr Vorteil: Zu jedem Pull Request entsteht automatisch ein Vorschau-Link (bei Netlify „Deploy Preview“ genannt). So testest du auf dem Box-Handy, bevor du übernimmst. Einrichten: Konto anlegen, GitHub verbinden, Repository auswählen, als Ausgabeordner (Netlify: „Publish directory“, Cloudflare: „Build output directory“) den Ordner eintragen, den Claude dir nennt. Einen Build-Befehl braucht die App nicht, das Feld bleibt leer. Die Bedingungen der Gratis-Tarife ändern sich – vor dem Einrichten auf der Webseite des Anbieters prüfen.

9.4 Wie die App aufgebaut ist

Herzstück ist der Analyse-Kern (Kapitel 7): das Programmteil, das aus einem Foto die Zahlen macht. Werkstatt und Handy-App benutzen dieselbe Datei. Dasselbe Foto ergibt deshalb am PC und auf dem Handy dieselben Werte, und was du in Etappe 4 eingestellt hast, gilt auch in der App. Abbildung 9.2 zeigt, wie die Teile zusammenhängen.

Die automatischen Tests sind deine Versicherung: Zu jedem Referenzbild ist das Ergebnis als Sollwert gespeichert. Bei jedem Pull Request rechnet GitHub alle Referenzbilder neu. Verschiebt eine Änderung die Ergebnisse, erscheint ein rotes Kreuz – auch wenn Claude das gar nicht vorhatte. Ist die Verschiebung gewollt (z. B. neue Schwellwerte nach der Kalibrierung, Kapitel 10), trägt Claude neue Sollwerte ein, erhöht die Algorithmus-Version (9.8) und zeigt dir, welche Werte sich geändert haben.

So ungefähr wird das Repository aussehen. Die genaue Ordnerstruktur legt Claude in B1 fest und beschreibt sie in CLAUDE.md:

  • kern/ – Analyse-Kern · werkstatt/ – Analyse-Werkstatt · app/ – Handy-App
  • bibliotheken/ – jsQR, SheetJS, JSZip als Dateien, damit alles offline läuft
  • tests/ – automatische Tests und Sollwerte · referenzbilder/ – deine Pilotfotos mit Bonitur (Kapitel 6.7)
  • docs/ – Spezifikation, Fortschritt, Pilotbericht, Beispielbilder · .github/workflows/ – Anweisungen für GitHub Actions

Was ist eine PWA, und wie geht offline?

Eine PWA (Progressive Web App) ist eine Webseite, die sich wie eine App verhält: eigenes Symbol auf dem Startbildschirm, eigenes Fenster ohne Adressleiste, kein App Store, kein Entwicklerkonto. Beim ersten Öffnen lädt das Handy alle Programmteile herunter. Ein Service Worker – ein kleines Hilfsprogramm im Browser – legt sie in einen Zwischenspeicher. Danach startet die App auch ohne Internet. Deine Messungen und Fotos speichert sie in der IndexedDB, einer Datenbank im Browser des Handys.

Zwei Folgen: Updates kommen nur an, wenn du die App ab und zu mit Internet öffnest. Und der Browser-Speicher ist kein Archiv – wer in Chrome die Browserdaten löscht, kann alle Messungen löschen. Bei knappem Speicher darf der Browser Daten sogar selbst aufräumen, wenn die App keinen „dauerhaften Speicher“ bekommen hat; deshalb fordert sie ihn an (B3). Trotzdem gilt: nach jeder Sitzung exportieren (B8, Kapitel 11.3).

9.8 Testen, Fehler melden, Versionen

Die automatischen Tests prüfen die Rechnung. Ob die App an der Box im Alltag funktioniert, prüfst nur du. Teste immer auf dem Box-Handy in der Box, mit eingeschalteten LEDs und echten Töpfen – nicht nur am PC.

Wie du vor dem Übernehmen an die neue Version kommst

  • Netlify oder Cloudflare Pages: Zu jedem Pull Request entsteht automatisch ein Vorschau-Link. Du findest ihn im Pull Request (als Kommentar oder in den Details zum Prüf-Status des Dienstes) oder in deinem Konto beim Dienst. Öffne ihn auf dem Box-Handy in Chrome. Die Vorschau hat eine eigene Adresse und damit einen eigenen Speicher: Deine echten Sitzungen siehst du dort nicht, und Testdaten landen nicht in der echten App. Leg dort eine Test-Sitzung an.
  • GitHub Pages: Eine Vorschau je Pull Request ist nicht eingebaut. Claude schlägt dir in B3 einen Weg vor (Punkt 5 im Prompt). Einfachster Notbehelf, solange nur du die App nutzt: kleine Änderung übernehmen, sofort testen, bei einem Fehler rückgängig machen (unten).

Checkliste für jeden Test

  • Im Pull Request steht bei den Tests ein grüner Haken.
  • Die App zeigt die neue app_version (sonst: mit Internet neu öffnen, Hinweis „Neue Version“ antippen).
  • Das Neue funktioniert so, wie Claude es beschrieben hat – Schritt für Schritt nach Claudes Test-Anleitung.
  • Das Alte funktioniert noch: kurzer Rundgang mit einem Topf – Sitzung starten, Foto, Ergebnis, Speichern, Export.
  • Flugmodus an, App schließen und neu öffnen: Sie startet, frühere Sitzungen sind noch da (in der Vorschau: deine Test-Sitzung).
  • Alles ist gut lesbar, die Knöpfe sind groß genug, nichts ist abgeschnitten.
  • Bei Änderungen an der Analyse: Kontrollbilder von 3 Töpfen verschiedener Stärke sehen plausibel aus.

Einen Fehler melden

Je genauer die Beschreibung, desto schneller die Lösung. Mach einen Screenshot (bei den meisten Android-Handys: Ein-/Aus-Taste und Leiser-Taste gleichzeitig), hol ihn wie die Fotos per USB-Kabel auf den PC (Kapitel 5.5) und füge ihn in die Sitzung ein, sofern deine Claude-Oberfläche das Anhängen von Bildern anbietet; sonst beschreibe genau, was auf dem Bildschirm steht. Schreib den Fehler in dieselbe Sitzung, wenn der Pull Request noch offen ist – sonst in eine neue.

9.9 Regeln für die Zusammenarbeit

  1. Ein Baustein pro Sitzung. Neuer Baustein, neue Sitzung. Lieber drei kleine Pull Requests als ein großer.
  2. Immer lesen lassen. Jeder Baustein-Prompt ab B2 lässt Claude zuerst CLAUDE.md, KONZEPT.md, docs/SPEZIFIKATION.md und docs/FORTSCHRITT.md lesen – Claude erinnert sich nicht an frühere Sitzungen. Eigene Prompts beginnst du genauso.
  3. Ziel beschreiben, nicht die Lösung. „Die Mitarbeiter sollen den Topf in 15 Sekunden erfassen“ hilft Claude mehr als „Mach den Knopf grün“. Zahlen und Beispiele helfen immer.
  4. Erst den Plan, dann den Code. Passt der Plan nicht, sag es sofort – Korrekturen am Plan kosten nichts.
  5. Fragen ist erlaubt. „Warum?“, „Was heißt das?“, „Gibt es einen einfacheren Weg?“ – so oft du willst.
  6. Nur Getestetes übernehmen. Grüner Haken und Test auf dem Box-Handy. Nie bei rotem Kreuz.
  7. Entscheidungen festhalten. Im Projekttagebuch mit Datum; wichtige Entscheidungen lässt du Claude in docs/SPEZIFIKATION.md eintragen.
  8. Keine echten Daten ins Repository. Keine Messdaten, keine Namen, keine Passwörter oder PINs. Einzige Ausnahme: die Referenzbilder (Kapitel 6.7).
  9. Nicht selbst am Code ändern. Auch nicht „schnell“ über die GitHub-Webseite. Bitte Claude darum – dann laufen die Tests mit. Einzige Ausnahme: eine Datei für GitHub Actions, die Claude dir vorgibt (Kasten in 9.2).
  10. Bei Verwirrung neu anfangen. Dreht sich Claude nach zwei, drei Versuchen im Kreis: Sitzung beenden, Pull Request nicht übernehmen, neue Sitzung mit einer kurzen Zusammenfassung des Problems.
  11. Selbst prüfen. Claude kann sich irren. Was an der Box mit echten Pflanzen nicht stimmt, stimmt nicht – egal, was die Tests sagen.
